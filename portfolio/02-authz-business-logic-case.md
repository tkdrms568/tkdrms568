# Authorization & Business Logic Assessment

## 목적

단순 SQL Injection이나 XSS 재현보다, 실제 업무 서비스에서 중요도가 높은 **인증·인가와 업무 로직을 어떤 순서로 분석하고 판단하는지**를 보여주는 포트폴리오입니다.

특정 고객사의 실제 취약점 정보는 포함하지 않으며, 공개 가능한 [Security Lab](../security-lab/web-api/CASE_STUDY_AUTHZ.md)에 다계정·다부서 승인 시나리오를 구성해 동일한 판단 과정을 재현할 수 있도록 했습니다.

---

## Case Study · Multi-Role Expense Approval

가상의 비용 승인 서비스에는 Employee / Manager / Admin 역할과 A·B 부서가 존재합니다.

업무 규칙은 다음과 같습니다.

- Employee는 자신의 요청만 조회·제출
- Manager는 자신의 부서 요청만 승인
- 요청자는 자신의 요청을 직접 승인할 수 없음
- `draft → submitted → approved/rejected` 상태 전이 준수
- 모든 권한·업무 규칙은 서버에서 검증

이 구조를 통해 단순 IDOR뿐 아니라 **Object Authorization + Role Scope + State Machine + Separation of Duties**를 함께 검증합니다.

---

## 1. 권한 구조 파악

진단 시작 시 먼저 사용자 유형과 기능 차이를 정리합니다.

| 구분 | 확인 내용 |
|---|---|
| Employee | 본인 객체 조회·상태변경 범위 |
| Manager | 부서 단위 조회·승인 범위 |
| Admin | 전체 조회 범위 |
| 비로그인 | 인증 전 접근 가능한 기능 |

중요한 것은 화면에 메뉴가 보이는지가 아니라 **서버가 실제 권한과 업무 범위를 확인하는지**입니다.

---

## 2. 객체 단위 권한 검증

API의 `expenseId`를 기준으로 다음을 비교합니다.

- 본인 객체 / 타 사용자 객체
- 동일 부서 / 타 부서
- Employee / Manager
- 목록 / 상세 / 승인

단일 Endpoint에서만 접근이 제한되는지 보지 않고, **같은 객체를 사용하는 여러 기능에 동일한 정책이 적용되는지** 확인합니다.

---

## 3. Role과 Scope 분리

`role=manager`라는 사실만으로 승인 권한이 충분한 것은 아닙니다.

실제 승인 시에는 다음을 함께 확인해야 합니다.

- Manager 역할
- 요청과 Manager의 부서 일치
- 현재 요청 상태
- 요청자와 승인자의 동일 여부

즉 **Role 검증이 존재해도 Scope 검증이 빠지면 권한 취약점이 될 수 있습니다.**

---

## 4. 업무 상태 전이 검증

정상 UI에서는 `draft → submitted → approved` 순서로 동작하더라도 API가 Client의 상태값을 그대로 신뢰하면 단계를 건너뛸 수 있습니다.

따라서 다음을 확인합니다.

- 현재 상태를 서버가 확인하는가
- 허용된 다음 상태가 정의되어 있는가
- 사용자가 임의의 상태를 직접 지정할 수 있는가
- 동일 요청 반복 시 상태가 비정상적으로 변경되는가

---

## 5. Separation of Duties

승인 권한이 있는 사용자가 자신의 요청까지 승인할 수 있는지 확인합니다.

이 항목은 기술적인 Role Check만 보는 것이 아니라 **업무상 권한 분리가 실제 서버 로직에 반영되어 있는지** 확인하는 사례입니다.

---

## 6. 영향도 판단

권한 문제는 "다른 ID가 조회된다"로 끝내지 않습니다.

다음 내용을 함께 확인합니다.

- 다른 부서 정보까지 접근 가능한가
- 조회를 넘어 승인·수정 등 상태 변경이 가능한가
- 반복 수행 가능한가
- Manager 범위 전체로 확장 가능한가
- 업무 승인 프로세스 자체를 우회할 수 있는가

---

## 7. 개선 방향

- 서버 측 Object Authorization 적용
- Role과 업무 Scope를 함께 검증
- Client가 전달한 상태값을 직접 신뢰하지 않음
- 서버가 허용된 State Transition을 정의
- 요청자와 승인자 분리
- 목록·상세·수정·승인 Endpoint에서 동일 정책 적용
- 유사 업무 객체에 대한 확산 점검

---

## 8. 재점검

조치 후에는 기존 요청 한 건이 차단되는지만 보지 않습니다.

- 동일 객체의 다른 Endpoint
- 다른 사용자 조합
- 다른 부서 조합
- 조회 / 수정 / 승인
- 정상 업무 흐름
- 상태 전이 우회
- 자기 승인

을 다시 확인합니다.

---

## 이 Case Study에서 보여주는 역량

- 다계정 환경의 권한 구조 분석
- Object-level Authorization과 Role Scope 구분
- 업무 상태 전이 분석
- 화면 제어와 서버 검증 구분
- 기술 취약점과 업무 규칙을 함께 보는 관점
- 조치 이후 유사 기능까지 확산 재점검하는 방식
