# Authorization & Business Logic Assessment

## 목적

단순 SQL Injection이나 XSS 재현보다, 실제 업무 서비스에서 중요도가 높은 **인증·인가와 업무 로직 검증 방식**을 정리한 포트폴리오입니다.

특정 고객사의 실제 취약점 정보는 포함하지 않으며, 실무에서 반복적으로 사용해 온 검증 관점을 공개 가능한 형태로 정리합니다.

---

## 1. 권한 구조 파악

먼저 사용자 유형과 기능 차이를 정리합니다.

| 구분 | 확인 내용 |
|---|---|
| 일반 사용자 | 본인 데이터 조회·수정 범위 |
| 상위 권한 사용자 | 추가 기능 및 데이터 접근 범위 |
| 관리자 | 관리 기능 및 전체 리소스 접근 |
| 비로그인 사용자 | 인증 전 접근 가능한 기능 |

중요한 것은 화면에 메뉴가 보이는지가 아니라 **서버가 실제 권한을 확인하는지**입니다.

---

## 2. 객체 단위 권한 검증

API 또는 요청에서 다음과 같은 객체 식별값을 확인합니다.

- userId
- memberId
- orderId
- documentId
- fileId
- 기타 업무 객체 식별값

검증 시에는 정상 요청을 기준으로 객체 식별값을 변경한 뒤, 다른 사용자의 리소스에 접근 가능한지 확인합니다.

### 판단 기준

- 서버에서 소유권을 확인하는가
- 역할만 확인하고 객체 권한은 확인하지 않는가
- 조회와 수정의 권한 기준이 동일한가
- 목록에서는 제한되지만 상세 API에서는 노출되는가

---

## 3. 수평·수직 권한 검증

### 수평 권한
동일한 역할의 다른 사용자가 타 사용자의 정보나 기능에 접근할 수 있는지 확인합니다.

### 수직 권한
일반 사용자가 관리자·운영자 기능을 직접 요청했을 때 서버에서 차단되는지 확인합니다.

---

## 4. 업무 로직 검증

다음과 같이 정상적인 UI 흐름만으로는 확인하기 어려운 조건을 점검합니다.

- 단계 건너뛰기
- 순서 변경
- 동일 요청 반복
- 상태값 직접 변경
- 서버가 계산해야 할 값의 클라이언트 변조
- 제한 횟수나 조건 우회
- 화면에서 제한된 기능의 직접 API 호출

---

## 5. 영향도 판단

권한 문제는 단순히 "다른 ID가 조회된다"로 끝내지 않습니다.

다음 내용을 함께 확인합니다.

- 노출되는 정보 종류
- 수정·삭제 등 상태 변경 가능 여부
- 반복 수행 가능 여부
- 다른 기능으로 확장 가능한지
- 관리자·내부 기능으로 이어질 수 있는지

---

## 6. 개선 방향

- 서버 측 인증·인가 검증
- 객체 소유권 확인
- 역할과 리소스 권한을 함께 검증
- 공통 권한검증 로직 적용
- 직접 전달된 상태값을 신뢰하지 않도록 서버에서 재검증
- 유사 Endpoint 확산 점검

---

## 7. 재점검

조치 후에는 기존 요청이 차단되는지만 확인하지 않고 다음도 다시 봅니다.

- 동일 객체의 다른 Endpoint
- 조회 / 수정 / 삭제 각각의 권한
- 모바일·웹 등 다른 클라이언트 경로
- 유사 업무 기능

---

## 보여주고자 하는 역량

- 사용자·권한 구조를 빠르게 이해하는 능력
- 화면 제어와 서버 권한검증을 구분하는 능력
- API와 업무 흐름을 연결해 분석하는 능력
- 실제 영향 범위를 기준으로 위험도를 판단하는 능력
