# Security Assessment Methodology

## 개요

다수의 웹·모바일·API·C/S 환경을 진단하면서 사용해 온 판단 흐름을 정리한 문서입니다.

취약점 이름을 많이 나열하는 것보다 **서비스 구조를 이해하고, 실제 공격면을 우선순위화하고, 재현 가능한 근거를 만들고, 개선과 재점검까지 연결하는 것**을 중요하게 봅니다.

---

## 1. 사전 이해

진단을 시작하기 전에 다음 내용을 먼저 확인합니다.

- 서비스 목적과 주요 업무 흐름
- 사용자 유형과 권한 차이
- 로그인·세션 처리 방식
- 외부 연계 API와 데이터 흐름
- 파일 업로드·다운로드 등 상태 변경 기능
- 관리자 및 내부 업무 기능
- 모바일·C/S 등 별도 클라이언트 존재 여부
- 테스트 가능 범위와 운영 영향

이 단계에서 단순 URL 목록이 아니라 **실제로 보안 검증이 필요한 기능과 데이터 흐름**을 구분합니다.

---

## 2. 공격면 정리

### Web / API
- 인증·인가
- 세션
- 입력값 처리
- 파일 처리
- 중요정보 노출
- 상태 변경 요청
- 업무 로직
- API 객체 및 권한 검증

### Mobile
- 앱 내부 보안 로직
- Root Detection 등 단말 보안 기능
- 앱과 API 간 통신 흐름
- 런타임 데이터 및 메모리
- 클라이언트 측 검증 의존 여부

### C/S
- 클라이언트 로직
- 서버 통신 구조
- 클라이언트 측 검증
- 내부 기능 및 권한 처리
- 로컬에 포함된 중요정보

### AI Service
- Prompt Injection
- 시스템 지시 우회
- 내부정보 노출 가능성
- 민감정보 처리
- 서비스 정책 우회

---

## 3. 우선순위

다음 조건을 우선적으로 확인합니다.

1. 권한이 달라지는 기능
2. 개인정보·중요정보를 처리하는 기능
3. 사용자 입력이 서버 처리에 직접 영향을 주는 기능
4. 파일 업로드·다운로드 기능
5. 관리자 또는 내부 업무 기능
6. 외부 시스템과 연계되는 API
7. 클라이언트 측 검증 비중이 높은 기능

모든 항목을 동일하게 보는 것이 아니라 **실제 악용 가능성과 서비스 영향이 큰 영역부터 확인**합니다.

---

## 4. 검증 방식

### 정상 동작 기준 확보
먼저 정상 요청·응답과 사용자별 기능 차이를 확인합니다.

### 변조
파라미터, 객체 식별값, 입력값, 세션·권한 조건 등을 변경해 서버가 어떤 방식으로 검증하는지 확인합니다.

### 비교
- 정상 / 비정상
- 일반 사용자 / 관리자
- 본인 리소스 / 타 사용자 리소스
- 클라이언트 제어 / 서버 제어

간 차이를 비교합니다.

### 영향 확인
단순 오류나 반응 차이만으로 취약점으로 판단하지 않고 **실제로 어떤 정보나 기능에 영향을 줄 수 있는지** 확인합니다.

---

## 5. Finding 판단 기준

Finding에는 최소한 다음 내용이 포함되어야 한다고 봅니다.

- 발생 위치
- 재현 조건
- 정상 동작과 취약 동작의 차이
- 발생 원인
- 실제 영향
- 조치 방향
- 재점검 방법

재현 가능성이나 영향이 부족한 항목은 확정 취약점과 구분합니다.

---

## 6. 개선 및 재점검

개선 가이드는 단순히 "필터링 필요"처럼 작성하지 않고 가능한 경우 다음까지 설명합니다.

- 어느 지점에서 검증해야 하는지
- 서버 측 검증이 필요한 이유
- 동일 문제가 반복될 수 있는 유사 기능
- 운영 환경에서 적용할 때 고려할 사항

조치 이후에는 동일 시나리오뿐 아니라 **우회 가능성과 유사 기능까지 다시 확인**합니다.

---

## 7. PM / PL 관점

PM/PL 역할에서는 개인 진단 결과뿐 아니라 다음을 함께 관리합니다.

- 진단 범위와 일정
- 프로젝트 내 주요 이슈
- Finding의 근거와 재현성
- 위험도와 표현의 일관성
- 고객·개발·인프라 담당자 커뮤니케이션
- 산출물 품질
- 조치 및 재점검 진행상황

---

## 핵심 원칙

> 서비스 구조를 이해하고 공격면을 정리한 뒤, 실제 악용 가능성과 서비스 영향을 근거로 판단하고 개선까지 연결합니다.
